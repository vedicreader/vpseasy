Multipass for local testing

Multipass runs Ubuntu virtual machines on your own computer. Testing a cloud-init file and a deploy on one costs nothing and takes a few minutes, so it is worth doing before you create a real server. Install Multipass and make sure the multipass command is on your PATH.

Multipass wraps that command. launch starts a VM, optionally with a cloud-init file from multi_init or vps_init and with host folders mounted inside it (mounts={host_path: vm_path}). vms lists VM names, ip gives a VM’s address, exec_ runs a command inside it and rm deletes it. Any other subcommand works as a method too, so mp.info('testvm') runs multipass info testvm. The module creates one instance for you as mp.

deploy_mp is deploy for a VM. It makes sure the target directory exists and belongs to the deploy user, then copies your app in and starts it. The cell below lists the VMs on the machine that built these docs, which had none.

Cloud-init generation

A new cloud server starts as a bare Ubuntu image. Cloud-init is the program that runs on its first boot and sets it up from a YAML file supplied when the server is created: it installs packages, creates users, adds SSH keys and runs commands. The two functions here write that file. Both return an AttrDict with the YAML text as yaml and the path of the matching private key as key.

vps_init is for a public server, on Hetzner or Lightsail. It builds the file with fastcloudinit’s cloud_init_config, which turns on the UFW firewall with only SSH allowed, adds log rotation and reboots at the end. vpseasy adds the fail2ban and unattended-upgrades packages and, unless docker=False, installs Docker and puts the user in the docker group. Other keyword arguments go to cloud_init_config.

multi_init is for a Multipass VM. It uses the smaller cloud_init_base, with the same user and Docker setup but no firewall and no fail2ban, so the VM boots faster. It reboots only when there are commands to run, and the Docker install counts as commands.

Both create one user, deploy by default, who can use sudo without a password and logs in only with the SSH keys in pub_keys. If pub_keys is left out, gen_key makes a new ed25519 key pair at ~/.ssh/<hostname>, replacing any key already there, and key points at it. Otherwise key is None. Extra packages go in pkgs and extra shell commands in cmds; the commands run after the Docker install.

vps_init also adds a swap file, 4 GB by default, and sets the kernel’s swappiness to 10, so the server swaps only under real memory pressure. A small server running several containers would otherwise kill a process when memory runs out. Pass swap=None to leave swap alone, or another size such as swap='2G'. swap_cmds returns those commands on their own, for a server that already exists.

The first test below passes a key, so none is generated. The second generates one and deletes it again.

Hetzner

Hetzner manages servers on Hetzner Cloud through the hcloud Python SDK, so you do not need Hetzner’s command-line tool or a config file. It reads the API token from HCLOUD_TOKEN unless you pass token=, and raises ValueError if there is none.

create makes a server and returns its IP address, name, key path and the raw SDK response. Give it the result of vps_init as cloud_init, and the key path comes back with the server. ssh_keys is a different way to log in. It names keys stored in your Hetzner account, and Hetzner adds them to the root user only. They give no access to the deploy user that cloud-init creates, so create refuses to take both. key_names lists the stored keys for that purpose.

servers lists your servers with their IP and status, get returns one by name or None, server_ip returns its address and delete removes it. Deleting a server that does not exist does nothing.

Lightsail

Lightsail is Amazon’s fixed-price VPS service. Lightsail has the same methods as Hetzner (servers, get, server_ip, create and delete) and talks to AWS through boto3, so vps_deploy works with either. boto3 is an optional extra: pip install 'vpseasy[aws]'. Credentials come from the standard AWS chain, for example an SSO profile named in AWS_PROFILE or passed as profile=. The region defaults to ap-southeast-2 (Sydney).

create is safe to run twice: an instance that already exists is not created again. Either way it waits until the instance is running, attaches a static IP address named <name>-ip, sets the open public ports to ports and turns on a daily automatic snapshot at snapshots. By default only SSH is open, since web traffic arrives through the Cloudflare tunnel, and the snapshot is taken at 16:00 UTC. delete removes the instance and releases its static IP. bucket makes a storage bucket for backups and is covered with Litestream below.

Lightsail runs user data as a shell script and does not read cloud-config YAML, so create converts a vps_init file with cloud_init_sh. The script sets the hostname, turns off password logins, creates the users with their groups, sudo rules and SSH keys, writes files, applies apt settings, installs packages and runs the commands, in that order. It does not reboot. It keeps the original YAML in /var/lib/vpseasy/cloud-config.yaml and logs to /var/log/vpseasy-init.log. When it finishes it creates /var/lib/vpseasy/ready, or /var/lib/vpseasy/error if a step failed, and chk_cloud_init reads those files. cloud_init_sh raises ValueError for any cloud-config key it cannot convert. Running cloud-init itself on the YAML in /etc/cloud/cloud.cfg.d was tried on Ubuntu 24.04 and did not create the users, which is why the conversion exists.

SSH helpers

These functions call the system ssh and rsync commands, so there is no Python SSH library to install. They share a few arguments. user (or u) is the login name, deploy by default. The private key is found in this order: the path in key (or k); then ~/.ssh/<name> if you pass name, which raises FileNotFoundError when no file is there; then whatever ssh would use by itself. key_pass is the passphrase of an encrypted key and password is a login password for servers that accept one. Pass True to either to be asked for it. The first connection to a new host adds it to known_hosts without asking.

run_ssh runs one or more commands on the host, joined with &&, and returns their output, with anything written to stderr appended after ;;. If a command fails it raises IOError, unless you pass check=False, in which case it returns (exit code, output). stdin_data is sent to the remote command’s standard input.

sync copies a local directory to path on the host with rsync. It first creates path with sudo if it is missing or not writable. It deletes remote files that are not in src, so point it at a directory that belongs to the app alone. exclude skips files that match a pattern. include works the other way round: only matching files are copied, and a pattern ending in / takes a whole directory. extra adds rsync flags such as --checksum.

sync raises CalledProcessError when rsync fails, so nothing runs on a half-copied folder; with check=False it returns rsync’s exit code instead.

sync_paths copies chosen paths rather than a whole folder, for content that changes without a rebuild, such as the files behind a bind mount. Each path under src goes to the same path under path, with one rsync per path, so --delete removes only files inside that path and never reaches the rest of the server’s folder. A path missing from src is skipped, and rsync’s --mkpath creates missing remote folders. last names a pattern held back from a first pass and sent in a second one. Use it when something on the server watches for one kind of file, so that the files beside it land first: with last='*.json', an audio file is in place before the JSON that names it. A path that names the folder itself, such as ., '' or /, or one that resolves to it or leaves it, through .. or a symlink, raises ValueError, since its --delete would reach the whole folder. dry_run=True lists the changes without making them, and with host=None the copy goes to a local folder, which is handy for tests. rsync_cmds returns the commands without running them.

deploy runs sync, then docker compose up -d --remove-orphans in path, adding --build unless build=False. It starts Compose only if Docker works for the user and path holds a docker-compose.yml; otherwise it stops after copying. chk_docker is that Docker check on its own and returns True or False. After a build, deploy keeps the new image and the one it replaced with keep_image, so rollback can return to either; keep=0 turns that off. After the build, prune=True deletes dangling images and the build cache, which otherwise grow by the size of an image on every deploy. Kept images carry tags, so pruning leaves them.

ssh_cmd, res_key and askpass_env are the pieces these functions share: the ssh command line, the key lookup, and a context manager that answers a password prompt. They are public for callers that run their own ssh or rsync. Every function that connects takes port, for servers whose SSH listens somewhere other than 22.

vps_deploy is the function most people want. It takes a server name, a local directory and a provider such as Hetzner() or Lightsail(). Rollback

A deploy builds a new image and replaces the running container, and a bad build takes the site down with it. deploy therefore keeps the image it replaces, and rollback puts it back.

Compose names the image it builds for a service after the project folder and the service, so /srv/app with service app builds app-app:latest. Compose strips characters other than lower-case letters, digits, - and _ from the folder name, and so does vpseasy. Pass img when the project is named otherwise, by a name: in the Compose file or COMPOSE_PROJECT_NAME; vps_deploy passes it on to deploy. A failed docker rmi, for a tag a stopped container still uses, leaves the tag and does not stop the deploy. After each build, keep_image tags the new image with its build time in UTC, such as app-app:20261019T063000, and tags the image that ran before it app-app:prev, also giving that one its build time when it has none. It then deletes the timestamped tags past the newest keep by build time, three by default, except the running image’s and prev’s. An image with two timestamps counts once, and a build whose second another build already holds takes the next free second. deploy runs keep_image even when the restart after a build fails, since the new build already holds latest. Every build keeps its tag until it falls out of the newest keep, whatever rollbacks happen in between, so no build loses its last tag while it is still among them. Pruning after the build deletes only dangling images, so the kept ones stay. kept_images lists the kept tags, newest first, with their image IDs.

rollback points the service at a kept image and restarts it. Without to, it picks the newest kept image older than the running one, so calling it twice goes back two builds. With to, it uses that tag, a timestamp or prev. Before switching, it tags the running image prev, so prev always names the image that ran before the current one and rollback(host, 'prev') undoes the last deploy or rollback. A rollback moves only latest and prev: the running image keeps its timestamp, so rollback(host, to=<its tag>) returns to it after any number of rollbacks. vpseasy 0.0.25 and earlier tagged the replaced image undo; that tag is no longer written or read. The restart is docker compose up -d --no-build --force-recreate for the one service, so Compose uses the retagged image and does not build.

A rollback restores the image and nothing else. Files that sync copied to the server, such as the Compose file, the Caddyfile and bind-mounted folders, stay as the last deploy left them, and so do volumes and databases. The next deploy builds from your source again and keeps the rolled-back image like any other.

    'A stand-in server: the commands `run_ssh` sends read and change a table of images, with their build times, and their tags.'
    def __init__(self, tags=None):
        self.tags, self.cmds, self.kw, self.n = dict(tags or {}), [], [], 0
        self.imgs = {i: '' for i in self.tags.values()}
    def __call__(self, host, *cmds, **kw):
        self.kw.append(kw); out = []
        for c in cmds:
            self.cmds.append(c); w = c.replace("'", '').split()
            if c.startswith('docker image inspect'):
                i = self.tags.get(w[5], w[5] if w[5] in self.imgs else '')

            elif c.startswith('docker image prune'): self.imgs = {i: t for i, t in self.imgs.items() if i in self.tags.values()}

Docker Compose helpers

Most small web apps deployed with vpseasy run as the same group of containers. There is the app itself, Caddy as the web server in front of it, and usually a cloudflared container that connects to a Cloudflare tunnel, so the server needs no open web ports. They share a network called web, and Caddy keeps its certificates and settings in two named volumes, caddy_data and caddy_config. caddy_stack writes that Compose file in one call.

It takes the domain and a Dockerfile object from dockeasy, such as fasthtml_app(). It saves the Dockerfile, Caddyfile and docker-compose.yml into root, or into the current directory when root is not given, and returns the Compose object. vols are container directories whose contents should stay on the server’s disk. vols_to_binds turns each into a bind mount from a folder of the same name beside the Compose file, so /app/data is stored in ./data. The app reads environment variables from env_file, .env by default. cloudflared=False leaves the tunnel out and makes Caddy listen on ports 80 and 443. conf puts the Caddyfile somewhere else, and other keyword arguments go to dockeasy’s caddy_svc, for example email= or dns=.

app_kw, caddy_kw and cloudflared_kw add settings to one service each, such as mem_limit='3g' or init=True. A volumes list in them is added to the service’s own volumes rather than replacing them, so caddy_kw=dict(volumes=['./static:/srv/static:ro']) lets Caddy serve files from the deploy folder. Pass your own dockeasy Caddyfile as caddyfile to write it instead of the one built from the options, or write_caddyfile=False to leave the Caddyfile alone. Without conf, the Caddyfile sits in root beside the Compose file and is mounted as ./Caddyfile, so the stack works wherever root is. The litestream argument is covered in the next section.

Litestream

Litestream copies every change to a SQLite database into an S3-compatible storage bucket, and can restore the database from that copy. The bucket can come from Lightsail.bucket, AWS S3 or Cloudflare R2.

litestream_conf writes Litestream’s config file and returns its text. dbs are absolute paths inside the container. If you pass vols, each database must sit inside one of them, or the Litestream container would not see it. Each database is stored at <prefix>/<db path> in the bucket, so two databases with the same file name do not collide. Litestream reads the access key from LITESTREAM_ACCESS_KEY_ID and LITESTREAM_SECRET_ACCESS_KEY, which go in .env. The format was tested against litestream/litestream:0.5 (v0.5.17). Litestream ignores config keys it does not recognise without any warning.

litestream_svc returns the arguments for a Litestream service in Compose.svc(). It mounts the app’s volumes and the config file, and runs replicate unless you give another command.

You will rarely call either directly. caddy_stack(..., litestream=dict(dbs=..., bucket=..., endpoint=..., region=..., prefix=...)) writes the config and adds the services. A one-shot litestream-restore service runs restore -if-db-not-exists -if-replica-exists, which restores a database only when the file is missing and a copy exists in the bucket. The app waits for it to finish successfully, so a fresh server gets its data back before the app can create an empty database. The long-running litestream service starts after the app. With more than one database there is one restore service for each.
