Multipass for local testing

Multipass runs Ubuntu virtual machines (VMs) on your own computer. Use a VM to test a cloud-init file and a deploy before you create a real server. A VM costs nothing and takes a few minutes to start. Install Multipass and put the multipass command on your PATH.

Multipass wraps the multipass command. launch starts a VM. It takes an optional cloud-init file from multi_init or vps_init, and optional host folders to mount in the VM as mounts={host_path: vm_path}. vms lists the VM names. ip returns the address of a VM. exec_ runs a command inside a VM. rm deletes a VM. Any other multipass subcommand works as a method. For example, mp.info('testvm') runs multipass info testvm. The module creates one instance, mp.

deploy_mp is deploy for a VM. It creates the target directory if it is missing and gives it to the deploy user. Then it copies your app in and starts it. The cell below lists the VMs on the machine that built these docs. That machine had none.

Cloud-init generation

A new cloud server starts as a bare Ubuntu image. Cloud-init is a program that runs on the first boot of the server. It reads a YAML file supplied when the server is created. It installs packages, creates users, adds SSH keys and runs commands. vps_init and multi_init write that file. Each returns an AttrDict with the YAML text as yaml and the path of the matching private key as key.

vps_init is for a public server on Hetzner or Lightsail. It builds the file with cloud_init_config from fastcloudinit. That function turns on the UFW firewall with only SSH allowed, adds log rotation and reboots at the end. vps_init adds the fail2ban and unattended-upgrades packages. Unless you pass docker=False, it also installs Docker and adds the user to the docker group. Other keyword arguments go to cloud_init_config.

multi_init is for a Multipass VM. It uses the smaller cloud_init_base. The user and Docker setup are the same as in vps_init. multi_init sets no firewall, installs no fail2ban and adds no swap file. It reboots only when there are commands to run. The Docker install counts as commands.

Both functions create one user, deploy by default. The user can run sudo without a password. The user logs in only with the SSH keys in pub_keys. If you omit pub_keys, gen_key uses the ed25519 key pair at ~/.ssh/<hostname>. It makes the key pair when no private key is there. It reuses a private key that is already there and writes a missing .pub file from it. gen_key(hostname, replace=True) makes a new key pair. key is the path of the private key. If you pass pub_keys, key is None. Use pkgs for extra packages and cmds for extra shell commands. The commands run after the Docker install.

vps_init also adds a swap file and sets the kernel swappiness to 10. The swap file is 4 GB by default. A swappiness of 10 makes the server swap only under real memory pressure. Without swap, a small server that runs several containers kills a process when memory runs out. Pass swap=None to skip swap, or a size such as swap='2G'. Pass swappiness to change the value. The commands add the swap file only if /swapfile does not exist, and they run before the Docker install. swap_cmds returns the commands on their own, for a server that already exists.

Hetzner

Hetzner manages servers on Hetzner Cloud through the hcloud Python SDK, so you do not need Hetzner’s command-line tool or a config file. It reads the API token from HCLOUD_TOKEN unless you pass token=, and raises ValueError if there is none.

create makes a server and returns its IP address, name, key path and the raw SDK response. Give it the result of vps_init as cloud_init, and the key path comes back with the server. ssh_keys is a different way to log in. It names keys stored in your Hetzner account, and Hetzner adds them to the root user only. They give no access to the deploy user that cloud-init creates, so create refuses to take both. key_names lists the stored keys for that purpose.

servers lists your servers with their IP and status, get returns one by name or None, server_ip returns its address and delete removes it. Deleting a server that does not exist does nothing.

Lightsail

Lightsail is the fixed-price virtual private server (VPS) service of Amazon. Lightsail has the same methods as Hetzner: servers, get, server_ip, create and delete. It talks to AWS through boto3. vps_deploy works with either class. boto3 is an optional extra: pip install 'vpseasy[aws]'. Without boto3, Lightsail() raises ImportError. Credentials come from the standard AWS chain. For example, name an SSO profile in AWS_PROFILE or pass profile=. The region defaults to ap-southeast-2 (Sydney).

create is safe to run twice. It does not create an instance that already exists. In both cases it calls server_ip, which waits until the instance is running. server_ip raises TimeoutError after tout seconds (300 by default). If static_ip is True, the default, create then attaches a static IP address named <name>-ip. A static IP that is already allocated is reused. If ports is not None, create sets the open public ports to ports. If snapshots is set, create turns on a daily automatic snapshot at that time. By default only SSH (port 22) is open, because web traffic arrives through the Cloudflare tunnel. The default snapshot time is 16:00 UTC. delete removes the instance. Unless you pass release_ip=False, it also releases the static IP. bucket makes a storage bucket for backups. The Litestream section covers it.

Lightsail runs user data as a shell script. It does not read cloud-config YAML. When the user data starts with #cloud-config, create converts it with cloud_init_sh. Other user data passes through unchanged. The script runs these steps in order: it sets the hostname, turns off password logins, creates the users with their groups, sudo rules and SSH keys, writes files, applies apt settings, installs packages and runs the commands. It turns off password logins only when the YAML sets ssh_pwauth: false. The script does not reboot. It keeps the original YAML in /var/lib/vpseasy/cloud-config.yaml and logs to /var/log/vpseasy-init.log. When it finishes, it creates /var/lib/vpseasy/ready. If a step failed, it creates /var/lib/vpseasy/error instead. chk_cloud_init reads those files.

cloud_init_sh converts these top-level keys: hostname, users, write_files, apt, packages, runcmd, package_update, package_upgrade and ssh_pwauth. It ignores preserve_hostname, disable_root and power_state. It raises ValueError for any other top-level key, for a user key it cannot convert, and for an invalid write_files permission. The conversion exists because cloud-init did not create the users on Ubuntu 24.04 when it ran on YAML placed in /etc/cloud/cloud.cfg.d.

SSH helpers

These functions call the system ssh and rsync commands. No Python SSH library is needed. They share these arguments. user (or u) is the login name, deploy by default. The private key comes from the first of these that applies: the path in key (or k); then ~/.ssh/<name> if you pass name; then the key that ssh picks by itself. If you pass name and the file ~/.ssh/<name> does not exist, the function raises FileNotFoundError. key_pass is the passphrase of an encrypted key. password is a login password for servers that accept one. Pass True to either to be asked for it. Every function that connects takes port, the SSH port, which is 22 by default. The first connection to a new host adds it to known_hosts without asking.

run_ssh runs one or more commands on the host, joined with &&. It returns their output. If the commands wrote to stderr, run_ssh appends that text after ;;. If a command fails, run_ssh raises IOError. With check=False it returns (exit code, output) instead. stdin_data is sent to the remote command’s standard input.

sync copies a local directory to path on the host with rsync. If path is missing or not writable, sync first creates it with sudo and gives it to user. sync deletes remote files that are not in src. Point it at a directory that belongs to the app alone. exclude skips files that match a pattern. include copies only the files that match a pattern. A pattern that ends in / takes a whole directory. extra adds rsync flags such as --checksum.

sync raises CalledProcessError when rsync fails. Nothing runs on a half-copied folder. sync returns the rsync exit code. With check=False, a failed rsync returns its exit code instead of raising.

sync_paths copies chosen paths instead of a whole folder. Use it for content that changes without a rebuild, such as the files behind a bind mount. Each path under src goes to the same path under path. sync_paths runs one rsync per path. --delete removes only files inside that path. It never reaches the rest of the folder on the server. A path that is missing from src is skipped. rsync’s --mkpath creates missing remote folders. delete=False, mkpath=False and itemize=False turn off the matching rsync flags.

last names a pattern. rsync holds the files that match it back from a first pass and sends them in a second pass. Use last when something on the server watches for one kind of file. With last='*.json', an audio file is in place before the JSON file that names it.

A path that names the folder itself raises ValueError. Examples are ., '' and /. A path that resolves to the folder, or leaves it through .. or a symlink, also raises ValueError. Its --delete would reach the whole folder.

dry_run=True lists the changes without making them. With host=None, the copy goes to a local folder. sync_paths returns the rsync commands it ran. rsync_cmds returns the commands without running them. It raises the same ValueError.

deploy runs sync. Then it runs docker compose up -d --remove-orphans in path. It adds --build unless you pass build=False. It starts Compose only if Docker works for the user and path holds a docker-compose.yml. Otherwise it stops after the copy. chk_docker is the Docker check on its own. It returns True or False. After a build, deploy keeps the new image and the image it replaced with keep_image. rollback can then return to either image. keep=0 turns this off. After the build, prune=True deletes dangling images and the build cache. Without pruning, they grow by the size of an image on every deploy. Pruning leaves kept images, because they carry tags.

ssh_cmd, res_key and askpass_env are the functions the others share. ssh_cmd returns the ssh command line. res_key looks up the key. askpass_env is a context manager that answers a password prompt. They are public for callers that run their own ssh or rsync. _ssh, _res_key and _askpass_env remain as aliases.

Rollback

A deploy builds a new image and replaces the running container. A bad build takes the site down. deploy keeps the image that it replaces. rollback starts that image again.

Compose names the image that it builds for a service after the project folder and the service. The folder /srv/app with the service app builds app-app:latest. Compose removes characters other than lower-case letters, digits, - and _ from the folder name. vpseasy does the same, and it also drops a leading - or _. Pass img when the project has another name, set by name: in the Compose file or by COMPOSE_PROJECT_NAME. vps_deploy passes img on to deploy.

After each build, keep_image tags the new image with its build time in UTC, such as app-app:20261019T063000. It tags the image that ran before as app-app:prev. It also gives that image its build time when the image has none. Then it deletes the timestamped tags past the newest keep by build time. keep is three by default. It never deletes the tags of the running image and of prev. An image with two timestamps counts once. A build whose second another build already holds takes the next free second. deploy runs keep_image even when the restart after the build fails. The new build already holds latest. A build keeps its tag until it falls out of the newest keep, whatever rollbacks happen in between.

A failed docker rmi leaves the tag in place. This happens when a stopped container still uses the tag. The deploy continues. Pruning after the build deletes only dangling images and the build cache. Tagged images stay. kept_images lists the kept tags, newest first, with their image IDs.

rollback points the service at a kept image and restarts it. Without to, it picks the newest kept image that is older than the running one. Calling it twice goes back two builds. With to, it uses that tag, which is a timestamp or prev. rollback raises ValueError when no kept image is older than the running one. It also raises ValueError when the tag to is not on the server.

Before it switches, rollback tags the running image prev. prev always names the image that ran before the current one. rollback(host, 'prev') undoes the last deploy or rollback. A rollback moves only the tags latest and prev. The running image keeps its timestamp. rollback(host, to=<its tag>) returns to it after any number of rollbacks. vpseasy 0.0.25 and earlier tagged the replaced image undo. vpseasy no longer writes or reads that tag. The restart is docker compose up -d --no-build --force-recreate for the one service. Compose uses the retagged image and does not build.

A rollback restores the image and nothing else. Files that sync copied to the server stay as the last deploy left them. Examples are the Compose file, the Caddyfile and bind-mounted folders. Volumes and databases also stay as they were. The next deploy builds from your source again. It keeps the rolled-back image like any other.

wait_http requests url until it answers 200. It tries up to tries times, poll seconds apart. Each request times out after timeout seconds. It returns True when the URL answers 200 and False when the tries run out. Use it after deploy and before anything that needs the new version to be live, such as purging a CDN cache. ua sets the User-Agent header. Cloudflare refuses some library agents. Give ua a name of your own. wait_http verifies HTTPS against the operating system trust store through truststore. A root certificate added there, such as the certificate of a company proxy, verifies as it does in a browser. wait_http prints an error message when it differs from the previous one. A wait that does not succeed shows why.

Docker Compose helpers

Most small web apps deployed with vpseasy run as the same group of containers. The app container is the app itself. A Caddy container is the web server in front of it. A cloudflared container, usually present, connects to a Cloudflare tunnel. With the tunnel, the server needs no open web ports. The containers share a network named web. Caddy keeps its certificates and settings in two named volumes, caddy_data and caddy_config. caddy_stack writes the Compose file for this group in one call.

caddy_stack takes the domain and a Dockerfile object from dockeasy, such as fasthtml_app(). It saves Dockerfile, Caddyfile and docker-compose.yml into root, or into the current directory when you omit root. It returns the Compose object. vols are container directories whose contents stay on the disk of the server. vols_to_binds turns each one into a bind mount from a folder of the same name beside the Compose file. For example, /app/data is stored in ./data. The app reads environment variables from env_file, which is .env by default. cloudflared=False leaves the tunnel out and makes Caddy listen on ports 80 and 443. conf puts the Caddyfile at another path. Other keyword arguments go to caddy_svc from dockeasy, for example email= or dns=.

app_kw, caddy_kw and cloudflared_kw add settings to one service each, such as mem_limit='3g' or init=True. A volumes list in them is added to the volumes of the service. It does not replace them. For example, caddy_kw=dict(volumes=['./static:/srv/static:ro']) lets Caddy serve files from the deploy folder. Pass your own dockeasy Caddyfile as caddyfile to write it instead of the Caddyfile built from the options. Pass write_caddyfile=False to leave the Caddyfile alone. Without conf, the Caddyfile is in root beside the Compose file and is mounted as ./Caddyfile. The stack works wherever root is. The next section covers the litestream argument.

The caddy_stack call without root shows the Compose file for a FastHTML app with one data volume. It saves the files in the current directory.

Litestream

Litestream copies every change to a SQLite database into an S3-compatible storage bucket. It can restore the database from that copy. The bucket can come from Lightsail.bucket, AWS S3 or Cloudflare R2.

litestream_conf writes the Litestream config file and returns its text. dbs are absolute paths inside the container. A relative path raises ValueError. If you pass vols, each database must sit inside one of them. Otherwise litestream_conf raises ValueError, because the Litestream container cannot see the database. Each database is stored at <prefix>/<db path> in the bucket. Two databases with the same file name do not collide. region is auto by default. snapshot sets the snapshot interval, 24h by default. retention sets how long Litestream keeps snapshots, 72h by default. The config also sets a validation interval of 12 hours. Litestream reads the access key from LITESTREAM_ACCESS_KEY_ID and LITESTREAM_SECRET_ACCESS_KEY. Put both in .env. The config format was tested against litestream/litestream:0.5 (v0.5.17). Litestream ignores config keys that it does not recognise, without a warning.

litestream_svc returns the arguments for a Litestream service in Compose.svc(). It mounts the volumes of the app and the config file. It runs replicate unless you pass another command as cmd.

You will rarely call either function directly. caddy_stack(..., litestream=dict(dbs=..., bucket=..., endpoint=..., region=..., prefix=...)) writes the config and adds the services. A one-shot litestream-restore service runs restore -if-db-not-exists -if-replica-exists. That command restores a database only when the file is missing and a copy exists in the bucket. The app waits for the restore service to finish successfully. A fresh server gets its data back before the app can create an empty database. The long-running litestream service starts after the app. With more than one database, each database has its own restore service.
